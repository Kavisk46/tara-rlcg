# CONTRIBUTIONS.md

## TARA: Contributions Statement (Paper Planning Document)

**Purpose.** This document enumerates the scientific, engineering, experimental, and open-source contributions this project intends to claim, states plainly which of them are already demonstrated versus still prospective, and states plainly what the project does not claim. It is written as an internal planning artifact for drafting a paper's Contributions section and Limitations section, not as marketing copy. It should be revised whenever the underlying claim it describes changes status (e.g., moves from "prospective" to "demonstrated" once an experiment is run) and must be kept consistent with `PROJECT_SPEC.md`.

**Current implementation status, stated up front.** As of this document, four of the eight pipeline stages described in `PROJECT_SPEC.md` are implemented and tested: the Repository Parser, the Repository Context Extractor, the Task Classifier, and the Task-Guided Adaptive Router. Retrieval, context fusion, and LLM-based generation are not yet implemented. No dataset has been collected, no baseline has been run, and no experiment has been executed. Consequently, **every empirical claim in this document is prospective** — a stated intention and a falsifiable commitment, not a result. This is stated once here explicitly so it does not need to be re-qualified in every sentence below; §4 in particular should be read with this in mind throughout.

---

## 1. Main Contribution

The main contribution of this work is **not** a new retrieval algorithm, a new embedding model, or a new LLM. It is the explicit separation of *task-intent classification* from *retrieval execution* as its own inspectable, independently-testable, swappable pipeline stage in a repository-level code-generation system — together with the empirical question this separation is designed to answer: **does making retrieval-strategy selection an explicit, deterministic, explainable decision (rather than an implicit property of a single fixed retrieval mechanism, or an opaque property of a learned end-to-end system) measurably improve retrieval quality, generation quality, retrieval efficiency, or explainability, and if so, at what cost in system complexity?**

This is a claim about system design and about an evaluation methodology for testing that design, not a claim of a new algorithmic technique. The routing mechanism itself (a small, fixed taxonomy; a rule-based classifier; a priority-ordered policy chain; a planner that assigns execution parameters) is intentionally simple and largely composed of well-understood building blocks (rule engines, priority dispatch, capability-aware fallback). The contribution under test is whether *this specific, simple, and fully inspectable* arrangement is competitive with — or better than — retrieval approaches that do not make the task-classification step explicit, not that the arrangement is individually novel in its parts.

**What would falsify this contribution:** if task-aware routing fails to outperform a well-tuned fixed-strategy baseline (semantic-only or always-hybrid) on retrieval and downstream generation quality, at comparable or worse efficiency, the honest conclusion is that explicit task classification is not worth its added complexity for this problem — and the project's evaluation design (`PROJECT_SPEC.md` §23–§27) is built to surface that outcome clearly rather than to obscure it.

## 2. Secondary Contributions

These are contributions of narrower scope than §1, each independently useful even if the main hypothesis in §1 is not confirmed.

1. **A closed, 13-member task-intent taxonomy for routing** (`tara.core.types.TaskType`), and, separately, **a 6-category semantic taxonomy for conceptual understanding** (`docs/task_taxonomy.md`). These are deliberately two different artifacts for two different purposes — one optimized for cheap, deterministic routing; one optimized for articulating retrieval-relevant semantics (required context, retrieval signals, failure modes) independent of any routing implementation. **Reconciling the two into a single taxonomy is unresolved and is not claimed to have been done.**
2. **A deterministic, rule-based classification design**, offered as a concrete, inspectable, low-cost point in the design space for task-intent classification, and as a fair baseline against which a future learned classifier can be compared. The contribution is the demonstration that a non-learned approach is *implementable and testable* for this narrow 13-way decision problem, not a claim that it is superior to a learned approach — that comparison is explicitly future work (§7).
3. **A priority-ordered, first-match-wins policy chain** as a lightweight, fully auditable alternative to weighted voting or learned strategy selection for a small (7-member) target strategy space. Every routing decision is traceable to exactly one policy and carries a natural-language justification string by construction.
4. **The task-type-conditioned routing exception** (a `REFACTOR`-specific override that selects the most thorough retrieval strategy regardless of the raw classification signals) is presented here explicitly as a **stated design hypothesis**, not an established finding. It is a concrete, falsifiable claim about when signal-based routing should be overridden by task-type-specific domain knowledge, and it is designed to be directly tested by ablation (`PROJECT_SPEC.md` §26, A2).
5. **A context-capability-aware planning step**, in which the router downgrades a retrieval plan when the concrete repository's current state cannot support it (e.g., no embeddings computed yet, no populated graph), using only cheap, already-computed metadata rather than a traversal. This is a modest but distinct contribution: it treats routing as a function of both query intent *and* repository state, not query intent alone.
6. **A small set of cross-cutting conceptual observations about retrieval-relevant task semantics** (documented in `docs/task_taxonomy.md`): that exact-identity and topical-breadth requirements vary independently across task types; that some tasks retrieve a ground truth while others (e.g., feature implementation) retrieve only a proxy; that test code is disproportionately load-bearing context across task types beyond test generation itself; and that design rationale ("why") is a scarce resource distinct from implementation ("what"). These are offered as analytical observations that could inform future taxonomy or system design; **they are not empirically validated by this project** and should be treated as hypotheses for future annotation or user studies to confirm or refute.

## 3. Engineering Contributions

Unlike §1 and §2, the items in this section describe an already-existing, tested software artifact, not a prospective claim.

- **Repository Parser** (`tara.parsing`): a Tree-sitter-based structural fact extractor supporting eight languages (Python, JavaScript, TypeScript, Java, Go, Rust, C, C++), producing a validated, serializable `ParsedRepository` with per-symbol byte/line spans, docstrings, and import statements, plus Git commit provenance. Covered by a dedicated unit-test suite exercising real parsed repositories (not mocked ASTs).
- **Repository Context Extractor** (`tara.context`): construction of a directed repository graph (containment/definition/import edges, with call/inheritance/implementation edges reserved for future population on the same graph rather than a second one), an O(1)-average-case symbol index, and an optional, injectable dense-embedding layer — with no LLM call anywhere in this stage. Embedding generation is mockable in tests by design (an `Embedder` abstract interface), so the test suite never loads a real model.
- **Task Classifier** (`tara.classification`): a deterministic, LLM-free, ML-free rule engine with measured sub-10ms latency (enforced by a dedicated timing test, not merely claimed), full separation of feature extraction, rule evaluation, and decision combination into independently testable components, and 144 passing unit tests covering every task type, every retrieval-signal flag, and stated edge cases (empty, whitespace-only, and punctuation-only queries).
- **Task-Guided Adaptive Router** (`tara.routing`): a deterministic policy-and-planner architecture with measured sub-2ms latency (again, enforced by a dedicated timing test), full separation of strategy selection (policies) from execution parameter assignment (planner), and 51 passing unit tests, including all five worked routing examples verified end-to-end against the real classifier output, not against synthetic/hand-constructed classification objects alone.
- **An interface-first, dependency-injected architecture** across all four implemented stages: every stage is defined by an `abc.ABC` that downstream code and downstream research variants depend on, and every stage's collaborators are constructor-injected rather than internally instantiated. This is what makes the ablations proposed in `PROJECT_SPEC.md` §26 (e.g., swapping the router's policy set, disabling reranking, swapping the embedding model) implementable as configuration rather than as source-code forks — an engineering property with a direct methodological payoff for the experimental program in §4.
- **A cumulative, currently-passing test suite of 240 tests** across the four implemented stages, with no test in that suite depending on a live model, a live network call, or nondeterministic behavior.

The engineering contribution claimed here is that the system exists, runs, and is tested — not that its design choices are empirically validated as superior to alternatives. That distinction is the entire subject of §4.

## 4. Experimental Contributions

**Status: none of the items below have been executed as of this document.** This section describes the experimental program this project commits to running, and the specific contributions that program is designed to produce, once the retrieval, fusion, and generation stages (`PROJECT_SPEC.md` §19–§21) are implemented. It is written now, in advance of any result, so that the evaluation design is fixed before results exist — reducing the risk of post hoc rationalization of whatever outcome is eventually observed.

1. **A pre-registered, falsifiable hypothesis set (H1–H5)** covering classification feasibility, retrieval quality, generation quality, retrieval efficiency, and confidence calibration (`PROJECT_SPEC.md` §6), each tied to a specific statistical test and significance threshold fixed in advance (§23).
2. **A defined ablation matrix (A1–A9)** isolating the individual contribution of each non-trivial design decision in the router and fusion stages — including, notably, a direct test of the `REFACTOR` override described in §2 above (A2), a direct test of graph retrieval's marginal value (A3), and a direct test of whether reranking strategy matters (A5/A6). The contribution here is methodological: an evaluation design capable of attributing an observed effect (if any) to a specific component, rather than to the system as an undifferentiated whole.
3. **A defined baseline family** spanning a genuine floor (no retrieval at all), a naive-but-realistic default (fixed semantic-only retrieval, representing current common practice), a maximal-but-non-adaptive alternative (always-full-pipeline retrieval), and a sanity-check control (random strategy selection) — chosen specifically so that any measured advantage for task-aware routing can be distinguished from "more retrieval is generically better" (addressed by the always-full-pipeline baseline) or from "any routing beats no routing by chance" (addressed by the random baseline).
4. **A best-effort comparison protocol against external related systems** (AIRCoder, RepoFormer, AllianceCoder, and, where relevant, RepoGraph and STALL+), with an explicit, pre-committed fallback policy: reproduce if a public artifact permits it, clearly label as a re-implementation if only a description is available, or omit with a stated justification — rather than silently omitting an unfavorable or hard-to-reproduce comparison after the fact.
5. **An explicit commitment to reporting a negative or null result as a valid outcome.** If task-aware routing does not outperform the strongest fixed-strategy baseline once retrieval, fusion, and generation are implemented and evaluated, that finding is itself a contribution of this project — a documented answer to a previously open, reasonably-posed question about repository-level retrieval-augmented code generation — and will be reported as such rather than reframed or suppressed.

Everything in this section is a commitment about *how* results will be produced and reported, not a description of results that exist.

## 5. Open Source Contributions

- **The `tara` codebase**, covering all implemented stages, released under an open license, with each stage's interface (`tara.interfaces.*`) designed to permit independent reuse — for example, the Repository Parser or the Repository Context Extractor could reasonably be adopted by an unrelated project needing a Tree-sitter-based structural fact extractor or a lightweight repository graph builder, without adopting the rest of TARA.
- **The specification and design-documentation suite itself** — `PROJECT_SPEC.md`, `docs/task_taxonomy.md`, and this document — released alongside the code as a transparent record of design intent, assumptions, and open questions. This is offered as a contribution independent of the empirical outcome: it allows a reviewer, a reproducer, or a future extender of this work to evaluate design decisions against their stated rationale, rather than having to reverse-engineer intent from code alone.
- **A planned, not-yet-executed dataset release**: the Task-Intent Query Set (TIQS, `PROJECT_SPEC.md` §22), a human-annotated set of developer queries labeled with task-intent and ground-truth relevant context. If successfully annotated at an acceptable inter-annotator agreement, this is intended as a standalone, reusable evaluation resource for future work on repository-level retrieval-augmented code generation generally, independent of whether TARA's own routing hypothesis is confirmed. **This is a planned deliverable, not a current one.**
- **A reproducibility posture as a process contribution**: pinned dependencies, configuration-driven (not hand-run) experiments, and a stated policy that no number is reported in the paper without an archived, re-runnable script producing it (`PROJECT_SPEC.md` §29–§30). This is a commitment about how the eventual empirical work will be conducted, offered here as a contribution to the project's own scientific hygiene rather than as a novel methodological technique.

## 6. Research Limitations

Stated candidly and without hedging, consistent with `PROJECT_SPEC.md` §27–§28:

- **No empirical evidence yet exists for the central hypothesis.** Everything in §1 and §2 is a claim under test. This document should not be read, and must not be cited, as evidence that task-aware routing works — only as evidence that a system capable of testing whether it works has been built.
- **The taxonomies (both the 13-member routing taxonomy and the 6-category semantic taxonomy) are hand-authored**, not derived from a large-scale corpus of real developer queries, nor validated against prior taxonomic work in software-engineering task modeling at scale. Their completeness, mutual exclusivity, and construct validity relative to how real developers actually phrase requests are unverified.
- **The classifier's rule-based design is a deliberate choice, not a demonstrated optimum.** This project shows that a cheap, deterministic classifier of this kind is implementable and testable; it does not show that this approach generalizes better, or worse, than a learned or LLM-based classifier — that comparison has not been run (§7).
- **Retrieval, context fusion, and generation are unimplemented as of this document.** No claim about end-to-end code-generation quality, and specifically no evidence bearing on H3, currently exists or can currently be made.
- **Generalization beyond the eventual, small, fixed repository corpus and eight supported languages is unverified.** The classifier's language-mention and naming-convention heuristics are English/Latin-alphabet-centric by construction and untested outside that setting.
- **Faithful reproduction of external baseline systems (AIRCoder, RepoFormer, AllianceCoder, RepoGraph, STALL+) is uncertain** and contingent on public artifact availability at the time the comparisons are run; some comparisons may end up qualitative/architectural rather than empirical, as stated in `PROJECT_SPEC.md` §24.
- **The `REFACTOR` override and any other hand-authored routing exception are design hypotheses**, justified by argument rather than by evidence at the time of writing, and are explicitly pending the ablation study described in §4, item 2.
- **The project's own dataset (TIQS) is authored, at least in part, by people aware of the taxonomy and the system under test**, which is a known circularity risk for classifier evaluation; the mitigation (independent annotators, inter-annotator agreement reporting, realistic rather than taxonomy-derived query construction) is described in `PROJECT_SPEC.md` §22 and §27 but does not eliminate the risk, only bounds it.

## 7. Future Work

- **A learned or LLM-based task classifier**, evaluated as a direct, head-to-head comparison against the rule-based classifier described in §3, rather than as an assumed replacement for it — directly testing the open question raised in §2, item 2 and §6.
- **Resolution of call-graph and inheritance-graph edges** (`CALLS`, `INHERITS`, `IMPLEMENTS`, currently reserved but unpopulated in the repository graph schema), enabling genuinely multi-hop graph retrieval beyond the current containment/definition/import structure.
- **Multi-hop or agentic retrieval** (deciding to retrieve again based on an intermediate result), explicitly out of scope for the current single-pass design but a natural next question once single-pass task-aware routing has been evaluated on its own terms.
- **Cross-repository retrieval**, for the common real-world case where relevant context lives in a separate but related repository (e.g., an internal shared library).
- **Extension to additional programming languages**, gated on Tree-sitter grammar availability and on evidence of demand, and explicit testing of whether the taxonomy and classifier heuristics (currently English/Latin-alphabet-centric) generalize to non-English queries and non-Latin identifier conventions.
- **Cost- and budget-aware routing**, in which the router optimizes not only for expected retrieval quality but for a stated latency or dollar-cost constraint per query — relevant once a real LLM generation cost exists to optimize against.
- **An active-learning or feedback loop** using low-confidence or empirically-misrouted queries (identifiable via the confidence-calibration analysis proposed in `PROJECT_SPEC.md` §25) to iteratively refine the taxonomy, the rule set, or, eventually, training data for the learned-classifier extension above.
- **Reconciliation of the two existing taxonomies** described in §2, item 1 — determining whether the 6-category semantic taxonomy should be merged into, replace, or remain deliberately separate from the 13-member routing taxonomy, informed by whatever the annotation process for TIQS reveals about real query distributions.
- **A production-oriented service layer** (authentication, multi-tenancy, scaling), explicitly deferred: the current and planned FastAPI layer (`PROJECT_SPEC.md` §12, §30) is a demonstration artifact for the research evaluation, not a foundation this extension is assumed to build on without redesign.
