# Learned Retrieval Router: Design Methodology

**Status.** Prospective design document. No model described here has been trained; no code implementing it exists. This document specifies *how* a learned router would be designed, trained, and evaluated, so that when the Router Training Set (RTS, `docs/DATASET_DESIGN.md`) becomes available, implementation can proceed against a fixed design rather than one improvised around whatever data happens to be easiest to use.

## Preliminaries

We formulate retrieval-strategy selection as a supervised multi-class classification problem: given a developer query and a set of signals describing it and the target repository, predict which member of TARA's seven-strategy taxonomy (`tara.routing.strategy.RoutingStrategy`) is expected to yield the best downstream retrieval and generation outcome. This formulation, and the model families we consider for it, are standard in the applied machine learning literature; nothing in this section claims algorithmic novelty. The contribution under study — consistent with `CONTRIBUTIONS.md` §1 and the central assumption named in `docs/methodology/Adaptive_Retrieval_Definition.md` §7 — is empirical: whether a model trained on labeled routing outcomes for *this specific problem* outperforms TARA's existing deterministic policy chain, not whether supervised classification itself is a new idea.

**Architectural constraint, stated once and binding throughout this document:** the learned router must be a new concrete implementation of the existing `tara.interfaces.router.Router` abstract contract — `route(classification, context) -> RetrievalPlan` — with no change to that interface, to `RetrievalPlan`, or to any downstream consumer. This is not a design preference; it is what makes the comparison against `AdaptiveRouter` (`DESIGN_DECISIONS.md` §2) a controlled one, substituting a single component while holding the rest of the pipeline fixed, exactly as `EXPERIMENT_PLAN.md`'s baseline methodology requires for every other system-variant comparison in this project.

## 1. Router Objective

The learned router's objective is threefold, each part directly answering an open question already posed elsewhere in this project's design documents rather than an objective invented for its own sake:

1. **Primary objective**, answering `docs/methodology/Adaptive_Retrieval_Definition.md` §10, open question 6: given the same class of inputs the deterministic router already consumes, plus the richer structural signals defined in `docs/DATASET_DESIGN.md` §2, predict a `RoutingStrategy` whose downstream retrieval and generation quality is at least as good as the deterministic policy chain's, ideally better, at a training and inference cost that does not itself violate the efficiency premise the project is testing (H4, `PROJECT_SPEC.md` §6).
2. **Secondary objective**, answering `docs/methodology/Adaptive_Retrieval_Definition.md` §10, open question 3: because the learned router's feature set is a strict superset of what the deterministic router uses (§2), a well-designed ablation program (§10 below) can attribute any observed improvement specifically to the richer input space, to the learned combination function, or to both — a decomposition the deterministic-vs-fixed-baseline comparisons in `EXPERIMENT_PLAN.md` cannot provide on their own.
3. **Tertiary objective**, preserving rather than discarding TARA's stated explainability contribution (`CONTRIBUTIONS.md` §1): the learned router must produce an explanation for its decision, not only a label, so that comparing it to the deterministic router's `reason` string is a comparison on equal terms, not an implicit trade of interpretability for accuracy.

## 2. Input Features

The input signal set is inherited directly from `docs/DATASET_DESIGN.md` §2 and is not re-derived here; this section restates it only to establish which fields are treated as model inputs, deferring the question of *how* each is encoded to §7.

| Category | Fields | Source |
|---|---|---|
| Query | Raw query text | TIQS / RTS |
| Task label | Full `TaskClassification` object: `task_type`, `confidence`, `graph_required`/`semantic_required`/`lexical_required`/`reasoning_required`, `extracted_keywords`, `detected_symbols`, `detected_file_paths`, `language_hint` | `tara.classification` (already implemented, reused unchanged) |
| Repository metadata | Domain category, split assignment | RTS manifest |
| Programming language | Primary language of the query's target file(s) | `tara.core.types.Language` |
| Repository size | Size bucket, plus raw `file_count`/`symbol_count` | `RepositoryContext` |
| Structural features | Query-complexity proxies (token count, detected-symbol count, quoted-identifier count, coordinating-conjunction indicator); repository graph statistics (node count, edge count, density); embedding availability (boolean) | `RepositoryContext`, engineered at feature-extraction time |

Two categories named as "candidate routing inputs" in `docs/methodology/Adaptive_Retrieval_Definition.md` §4 — latency budget and token budget — are excluded here for the identical reason given there: neither is operationalized anywhere in the current pipeline, and RTS itself does not capture them (`docs/DATASET_DESIGN.md` §2). A learned router trained today cannot condition on a signal that does not yet exist.

## 3. Output Labels

The router's training target is `best_strategy`, the seven-way categorical label defined in `docs/DATASET_DESIGN.md` §3, predicted at inference time as a full probability distribution over `RoutingStrategy` rather than a bare class label — the distribution is what allows a *model-derived* confidence to be computed (the maximum posterior probability, or one minus the distribution's normalized entropy), which is a distinct quantity from RTS's *label*-confidence field (`docs/DATASET_DESIGN.md` §3), itself never treated as ground truth for a "confidence" prediction. Conflating the two would repeat the exact category error that document was written to prevent.

Explanation generation is treated as a *derived*, not directly supervised, output. Rather than training the model to generate free text (which would require either a much larger labeled explanation corpus than RTS's gold subset provides, or an LLM call at inference time — the latter explicitly precluded by the "no LLM in the routing path" principle central to this project's design, `DESIGN_DECISIONS.md` §1), the router's explanation is constructed from the model's own feature attributions: the features contributing most to the predicted class are mapped, via a fixed template, onto a natural-language sentence structurally analogous to `RoutingDecision.reason`. This choice is revisited in §5 once model-family suitability is discussed, since it constrains which model families can support it faithfully.

## 4. Candidate ML Models

Given RTS's projected scale (2,000–5,000 training examples, `docs/DATASET_DESIGN.md` §6) and its predominantly structured, mixed-type feature set (§2), the candidate space is deliberately restricted to model families with an established record on small-to-medium tabular classification problems, rather than surveyed exhaustively.

| Candidate | Family | Role |
|---|---|---|
| Multinomial logistic regression | Linear | Required interpretable baseline |
| Gradient-boosted decision trees | Ensemble, tree-based | Primary candidate |
| Random forest | Ensemble, tree-based | Secondary candidate |
| k-nearest neighbors | Instance-based | Secondary candidate |
| Small feed-forward network over engineered features | Neural | Exploratory, contingent on data scale |
| Fine-tuned small text encoder over raw query text | Neural (text) | Exploratory, explicitly distinguished from LLM-as-router |

## 5. Why Each Model Is Suitable

**Multinomial logistic regression.** The natural floor: linear, closed-form-adjacent to fit, trivially fast at inference, and its coefficients are directly interpretable per feature-class pair — the most transparent possible explanation mechanism, at the cost of being unable to represent feature interactions (e.g., "graph availability matters only when `task_type` is `ARCHITECTURE`") that the deterministic router's own policy chain already encodes implicitly through its priority-ordered conditionals. Required as a baseline specifically because, per `CONTRIBUTIONS.md` §4's stated commitment to reporting negative results honestly, any more complex model's value must be justified relative to the simplest thing that could plausibly work.

**Gradient-boosted decision trees — the primary candidate.** This family is well suited to exactly the feature mix in §2: mixed categorical and continuous types with no need for scaling or one-hot expansion at the model level, native robustness to the missing-feature cases §7 discusses, and — most importantly for §3's explanation requirement — a mature, standard mechanism (per-feature contribution to a specific prediction, e.g. via Shapley-value-based attribution) for producing faithful, per-instance explanations, not merely global feature-importance rankings. Inference cost for a modest number of shallow trees is low-single-digit milliseconds at most, plausibly compatible with the deterministic router's existing latency budget, though this must be measured empirically once implemented (§8), not assumed.

**Random forest.** A reasonable alternative within the same tree-based family, typically requiring less hyperparameter tuning than gradient boosting at some cost in peak accuracy; included as a secondary candidate specifically to check whether gradient boosting's additional tuning complexity is earning its keep on a dataset this size, where boosting's usual advantage over bagging can be smaller than on larger corpora.

**k-nearest neighbors.** Included less as an accuracy candidate than as an interpretability check: a prediction explained as "this query is most similar to these three training examples, which were labeled X" is a qualitatively different, and for some readers more intuitive, form of explanation than a feature-attribution sentence. Its practical drawbacks — sensitivity to feature scaling and distance-metric choice, and query-time cost that grows with training-set size — make it unlikely to be the final choice, but a useful reference point in the ablation program (§10).

**Small feed-forward network over engineered features.** Offers strictly more representational capacity than the tree-based candidates for capturing feature interactions, but at RTS's projected scale this capacity is more likely to manifest as overfitting variance than as genuine generalization gain — a concern `docs/DATASET_DESIGN.md` §8 already raises structurally. Listed as exploratory: worth testing once RTS's realized size is known, not assumed viable in advance.

**Fine-tuned small text encoder over raw query text.** Distinguished explicitly from the LLM-as-router alternative already considered and rejected in `docs/methodology/Adaptive_Retrieval_Definition.md` §9: a small, locally-run, fine-tuned encoder producing a fixed classification head is deterministic at inference and does not incur per-query API cost or latency, unlike prompting a general-purpose LLM. It is listed as exploratory rather than primary because it would use only the `Query` input category, discarding the structured features (§2) that are, by construction, the majority of what distinguishes this router's input space from the raw query text a general-purpose text classifier would see — and because RTS's scale is modest even by fine-tuning standards for this model class.

## 6. Training Pipeline

Training proceeds against RTS's train split exclusively (`docs/DATASET_DESIGN.md` §6); the validation split is reserved for model-family selection and hyperparameter tuning, and the test split is touched exactly once, at final evaluation, per the sealing discipline already established for every other confirmatory result in this project (`DATASET_PLAN.md` §8, `EVALUATION_PROTOCOL.md` §14).

1. **Feature extraction.** Every RTS training example is transformed into a fixed-length feature vector via the frozen encoding pipeline defined in §7.
2. **Class-imbalance handling.** Given the possibility of an imbalanced `best_strategy` distribution flagged during RTS's own quality checks (`docs/DATASET_DESIGN.md` §5), training incorporates explicit class weighting (inversely proportional to observed class frequency) rather than assuming the raw label distribution is an appropriate training prior — directly motivated by the distribution-mismatch risk that document's §7 already names.
3. **Model-family and hyperparameter selection.** Each candidate in §4 is trained across a bounded hyperparameter search, selected by validation-split performance (§9's primary metric). Given RTS's modest scale, a resampling-based validation procedure (e.g., repeated random sub-sampling within the train split, distinct from and in addition to the held-out validation split) is used to reduce the risk of a single validation split's idiosyncrasies driving model selection.
4. **Calibration.** Because the router's predicted confidence (§3) is intended to support the same kind of downstream reasoning the deterministic classifier's confidence already supports (H5, `PROJECT_SPEC.md` §6), the selected model's output probabilities are explicitly calibrated post-training and checked via the identical Expected Calibration Error metric and reliability-diagram methodology already specified for the deterministic classifier (`EXPERIMENT_PLAN.md` §3) — reused, not reinvented, so a calibration comparison between the two routers is directly meaningful.
5. **Freezing and versioning.** The selected, calibrated model is versioned as a single artifact (weights/parameters plus the exact feature-encoding configuration from §7), frozen before any test-split evaluation, and archived under the same reproducibility discipline governing every other experimental artifact in this project (`EVALUATION_PROTOCOL.md` §14) — no result is reported against a model that could have been silently retrained since.

## 7. Feature Engineering

- **Categorical fields** (`task_type`, 13 levels; `Language`, 8 levels; repository size bucket, 3 levels) are one-hot encoded. This is chosen specifically over target/frequency encoding to preserve straightforward feature-attribution semantics for §3's explanation mechanism — a one-hot feature's contribution to a prediction has an unambiguous natural-language reading ("`task_type = REFACTOR` contributed X"), which a frequency-encoded numeric substitute would not.
- **Boolean fields** (`graph_required`, `semantic_required`, `lexical_required`, `reasoning_required`, embedding availability) are encoded directly as binary features.
- **Continuous fields** (classifier `confidence`, token counts, `file_count`, `symbol_count`, graph node/edge counts and density) are used unscaled for the tree-based candidates (§4), which are scale-invariant by construction, and standardized (zero mean, unit variance, computed on the train split only and applied unchanged elsewhere) for the linear and neural candidates.
- **Query text** is not fed to the primary tabular candidates as raw text. It is reduced to the complexity-proxy features already listed in §2, plus — as an explicitly optional, separately-ablated feature group (§10) — a dense sentence-embedding vector produced by the same `Embedder` abstraction already implemented for dense retrieval (`tara.context.embedder`). Including this vector is a deliberate, non-default option rather than a mandatory input: it couples the router's feature set to an embedding model's availability and adds an embedding-computation cost to every routing decision, including ones a purely lexical or graph-oriented strategy would not otherwise require — a tension directly analogous to why the deterministic router does not compute embeddings itself. Whether this cost is worth its accuracy contribution is an empirical question, not a design assumption, and is treated as such in §10.
- **Missing-value policy.** A feature that is structurally absent for a given example (most commonly, graph or embedding statistics for a repository lacking that data) is represented with an explicit "unavailable" indicator feature alongside a sentinel value, rather than imputed to a default such as zero. This preserves the same distinction the deterministic router's own capability-gate logic already makes (`DESIGN_DECISIONS.md` §2) between "this signal is absent" and "this signal is present but low," which a silent zero-imputation would erase.
- **Versioning.** The exact encoding configuration (one-hot vocabularies, standardization parameters, the embedding-model identifier if the optional query-embedding feature is enabled) is frozen and versioned together with the trained model per §6, since a feature-encoding change is, for reproducibility purposes, indistinguishable from a model change.

## 8. Inference Pipeline

At inference time, the learned router — realized as a new concrete class implementing `tara.interfaces.router.Router` — executes the following steps for a given `(classification, context)` pair, mirroring the two-stage separation already established by the deterministic router's own architecture (`DESIGN_DECISIONS.md` §2):

1. **Feature extraction**, applying the exact frozen transform from §7 to the incoming `TaskClassification` and `RepositoryContext`.
2. **Model forward pass**, producing a calibrated probability distribution over the seven `RoutingStrategy` values.
3. **Strategy selection**, by default the arg-max of the distribution; optionally gated by a confidence threshold below which the router falls back to a fixed default strategy rather than trusting a low-confidence prediction — directly reusing the confidence-gated-fallback design already scoped, but not yet implemented, for the deterministic router as ablation A7 (`EXPERIMENT_PLAN.md` §5). Implementing this mechanism once, generically, so both routers can use it, is preferable to building two separate fallback mechanisms.
4. **Explanation construction**, deriving a natural-language sentence from the selected model's per-instance feature attribution (§3, §5), not from a generative model call.
5. **Retriever-set resolution**, via the existing `STRATEGY_RETRIEVERS` mapping (`tara.routing.strategy`) — reused unchanged, since it is a property of the strategy taxonomy itself, not of which mechanism selected a strategy.
6. **Execution-parameter assignment**, by handing the resulting strategy and retriever set to the existing `RetrievalPlanner` (`tara.routing.planner`) unchanged. This is the single most important architectural consequence of this design: **the learned router replaces only the policy-selection half of the existing pipeline, never the planning half.** `RetrievalPlanner`'s responsibilities — deduplication, execution ordering, parallelism, top-k/candidate-limit assignment, graph-depth assignment, and, critically, the context-capability downgrade logic — are orthogonal to *how* a strategy was chosen, and were already implemented as a separate, independently injectable collaborator specifically so a second strategy-selection mechanism could be introduced without touching them (`DESIGN_DECISIONS.md` §2, §12). This document's design is, in effect, the first real exercise of that architectural bet.

Inference latency must be measured once implemented, under the same hardware-reporting discipline as every other timed result in this project (`EVALUATION_PROTOCOL.md` §8), and compared explicitly against the deterministic router's existing sub-2ms measured budget. Compatibility with that budget is a design goal for the primary candidate (§5) but is not assumed in advance.

## 9. Evaluation Metrics

Evaluation proceeds at two levels, both reusing existing project infrastructure rather than introducing router-specific metrics.

**Router-internal metrics**, analogous to the deterministic classifier's own evaluation (`EXPERIMENT_PLAN.md` §3): multi-class accuracy and macro-F1 over the seven `RoutingStrategy` labels on the RTS test split, a full confusion matrix (informative here specifically because certain strategy confusions, e.g. `HYBRID` vs. `FULL_PIPELINE`, are more benign than others, e.g. `LEXICAL_ONLY` vs. `GRAPH_ONLY`), and Expected Calibration Error on the predicted-confidence distribution.

**Downstream, pipeline-level metrics.** The learned router is not evaluated in isolation from the rest of the system: its predictions, run through the unchanged `RetrievalPlanner` and the full retrieval/fusion/generation pipeline, are scored on the identical retrieval-quality, generation-quality, and efficiency metrics already defined for every other system variant (`EXPERIMENT_PLAN.md` §3), against the identical TIQS test split, using the identical statistical procedure (paired Wilcoxon signed-rank, Holm–Bonferroni-corrected, BCa bootstrap confidence intervals — `EXPERIMENT_PLAN.md` §6, `EVALUATION_PROTOCOL.md` §6). Concretely, the learned router becomes a new system variant in the *existing* experimental design — compared directly against `AdaptiveRouter` and against every baseline already defined there — rather than the subject of a separate evaluation track. This is a deliberate design choice: building a second evaluation methodology for the learned router specifically would risk the comparison being apples-to-oranges by construction.

**Explanation quality.** The same explainability rating protocol already specified for the deterministic router's `reason` strings (`EVALUATION_PROTOCOL.md` §12) is applied unchanged to the learned router's feature-attribution-derived explanations, enabling a direct comparison of explanation quality between the two mechanisms — not only a comparison of routing accuracy.

## 10. Ablation Plan

| Ablation | Manipulation | Question answered |
|---|---|---|
| Feature-group: structural features | Remove query-complexity and graph-statistic features, leaving only what the deterministic router already uses | Does the richer input space (§1, objective 2) earn its keep, or does the learned combination function alone explain any observed gain? |
| Feature-group: query embedding | With vs. without the optional dense query-embedding feature (§7) | Does this feature's accuracy contribution justify its added inference cost? |
| Model family | Head-to-head comparison of every candidate in §4 on the identical train/validation split | Empirically grounds the a priori suitability argument in §5 |
| Confidence-gated fallback | With vs. without the low-confidence fallback mechanism (§8, step 3) | Mirrors ablation A7 already scoped for the deterministic router (`EXPERIMENT_PLAN.md` §5); tests the same mechanism generically across both routers |
| Training-set size | Train on 25% / 50% / 75% / 100% of the available RTS training examples | Informs whether additional labeling investment (`docs/DATASET_DESIGN.md` §6) would be worthwhile before further model development is prioritized |
| Label source | Train using oracle-derived labels only vs. oracle-plus-LLM-assisted-supplemented labels | Tests whether the lower-provenance labeling tier (`docs/DATASET_DESIGN.md` §4) helps or harms model quality when included |

## 11. Risks

- **Overfitting at RTS's projected scale.** Consistent with `docs/DATASET_DESIGN.md` §8's stated scope limitation, every candidate beyond the linear baseline carries meaningful overfitting risk at a few thousand examples; the training-set-size ablation (§10) is the primary instrument for detecting this, not merely a curiosity.
- **Label-noise propagation.** Any noise already present in RTS's `best_strategy` labels (oracle-metric noise, LLM-labeling circularity, human-annotation disagreement — all named in `docs/DATASET_DESIGN.md` §7) becomes noise the model is trained to reproduce, not merely noise it is evaluated against.
- **Distribution mismatch, now as a generalization risk rather than only a labeling risk.** A model trained on RTS's stratified, non-natural query distribution may encode that artificial balance as a learned prior over how often each task type or strategy should occur, a risk `docs/DATASET_DESIGN.md` §7 already raises and which applies with full force to a *trained* model, more so than to a benchmark merely *evaluated* against the same distribution.
- **Explainability regression across future iterations.** If a later iteration replaces the primary tree-based candidate with a less inherently interpretable model on the strength of an accuracy gain, explanation faithfulness could regress relative to both the deterministic router's exact `reason` string and this design's own feature-attribution mechanism — a risk to monitor at every future model-selection decision, not only at the first one.
- **Latency risk.** Model inference could exceed the deterministic router's measured sub-2ms budget; if the learned router is ever adopted as a default rather than kept as a compared alternative, this would directly bear on the project's efficiency claims (H4) and must be measured before any such adoption, not assumed.
- **Operational cost.** Unlike the deterministic router, whose logic is transparent, hand-editable, and requires no training pipeline, a learned router requires versioned model artifacts and a retraining process — an ongoing maintenance cost that must be weighed against any accuracy gain, applying `CONTRIBUTIONS.md` §1's "is the added complexity justified" question recursively to this router itself.
- **Circularity in the evaluation instrument.** Because RTS's oracle labels are computed using this project's own retrieval strategies and metrics (`docs/DATASET_DESIGN.md` §4), a learned router trained on them is, by construction, optimized against this project's own definition of "good retrieval." Any observed superiority over the deterministic router should be interpreted with this in mind — it demonstrates fitting the measurement instrument well, which is necessary but not sufficient evidence of genuinely better routing, echoing the construct-validity caution already raised for retrieval metrics generally (`EXPERIMENT_PLAN.md` §14).

## 12. Future Improvements

- **Confidence-and-outcome multi-task learning**: jointly predicting `best_strategy` alongside a downstream quality estimate, potentially improving calibration of both.
- **Online or continual learning** from production usage feedback, realizing the contextual-bandit alternative already named and set aside in `docs/methodology/Adaptive_Retrieval_Definition.md` §9 for lack of an online feedback loop — revisitable once one exists.
- **Learned explanation generation** via a small fine-tuned sequence-to-sequence head, if feature-attribution-derived explanations prove insufficiently faithful or fluent under the explainability rating protocol (§9).
- **Learned structural representations**, e.g. a graph neural network operating directly over `RepositoryContext.graph` in place of the hand-engineered graph-statistic features in §2 — a substantially larger architectural step, explicitly out of scope until RTS's scale and the simpler candidates' results justify it.
- **Cross-repository pretraining** on a larger, weakly-labeled query corpus (e.g., derived from public issue trackers) prior to fine-tuning on RTS's smaller gold-labeled set, directly addressing the overfitting risk named in §11.
- **Continuous strategy weighting.** If the learned router's output distribution proves more informative than its arg-max, a natural extension is to route by continuous multi-retriever weighting rather than discrete strategy selection — the alternative design already named and set aside for the deterministic router in `docs/methodology/Adaptive_Retrieval_Definition.md` §9, revisited here because a learned router, unlike a rule-based one, produces a distribution as a natural byproduct rather than requiring one to be separately engineered.
