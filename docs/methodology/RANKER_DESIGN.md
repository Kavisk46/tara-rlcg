# Learning-to-Rank Formulation of Retrieval Strategy Selection

**Status.** Prospective design document, reformulating the learned router previously specified in `docs/methodology/ROUTER_DESIGN.md` as a multiclass classifier. Per reviewer feedback, retrieval strategy selection is reformulated here as a Learning-to-Rank (LTR) problem. This document **supersedes** `ROUTER_DESIGN.md`'s modeling formulation but does not retract it as a comparison point: the classification-based router remains a legitimate, still-relevant system variant, and §6 explicitly proposes evaluating the ranking-based router *against* it, not only against the deterministic `AdaptiveRouter`. Nothing in this document has been implemented; no model has been trained.

**A load-bearing dependency this reformulation introduces, stated once here rather than discovered later:** Learning-to-Rank requires, for each training example, the *full* utility score across every candidate strategy, not a single arg-max label. `docs/DATASET_DESIGN.md` §3 currently specifies `best_strategy` (a single label) as the primary output schema field, with the full oracle-computed utility vector implied by the labeling procedure (§4 of that document, which computes a metric per strategy to determine the best one) but not committed to as a *retained, released* field. This document's feasibility is contingent on `DATASET_DESIGN.md` being revised to persist that vector. That revision is recommended, not performed, here.

---

## 1 Motivation

Formulating retrieval strategy selection as multiclass classification, as `ROUTER_DESIGN.md` did, requires reducing each training example to a single best-strategy label before the model ever sees it. This reduction is lossy in a way that is avoidable, and avoiding it is the motivation for this reformulation.

**Ranking uses more of the available supervision signal per example.** The oracle labeling procedure that produces RTS's `best_strategy` field (`docs/DATASET_DESIGN.md` §4) does not directly observe a single correct label — it computes a retrieval-quality (or, where available, generation-quality) metric for *every* candidate strategy and selects the maximum. The classification formulation discards every value in that computation except the identity of the maximizer. A ranking formulation retains the full ordering, and, where the underlying metric values are preserved, the full utility magnitudes as well. Given RTS's modest projected scale (2,000–5,000 labeled examples, `docs/DATASET_DESIGN.md` §6 — small relative to typical Learning-to-Rank literature, a point returned to in §10), extracting more supervisory signal per labeled example is not a marginal refinement; it is a direct response to a data-scarcity constraint this project already acknowledged for the classification formulation (`docs/DATASET_DESIGN.md` §8, `ROUTER_DESIGN.md` §11).

**Retrieval strategies are not mutually exclusive, and classification's decision boundary assumes they are.** TARA's seven-member strategy taxonomy (`tara.routing.strategy.RoutingStrategy`) already includes strategies that are explicit *combinations* of others — `HYBRID`, `GRAPH_PLUS_SEMANTIC`, `LEXICAL_PLUS_GRAPH`, and `FULL_PIPELINE` are compositions of the three atomic retrieval mechanisms, not independent alternatives to them. A multiclass classifier is nonetheless required to draw a hard decision boundary between, for example, `HYBRID` and `FULL_PIPELINE`, even though the underlying question — *how many, and which, retrieval mechanisms are worth their cost for this query* — is closer in character to a graded, compositional judgment than to a categorical one. A ranking formulation, which scores every candidate independently rather than partitioning the input space into disjoint regions, does not force this artificial boundary, and its output (§4) is a strictly more natural precursor to the continuous multi-retriever blending alternative already named and deliberately deferred in `docs/methodology/Adaptive_Retrieval_Definition.md` §9.

**Ranking preserves near-tie uncertainty that classification's own label-construction procedure already discards.** `docs/DATASET_DESIGN.md` §4 documents an explicit tie-breaking convention: when two or more strategies' oracle metrics fall within a margin, the *cheaper* strategy is preferred as the label. This convention is necessary for classification, which requires a single ground-truth label per example, but it is also direct evidence that the classification formulation destroys information the labeling procedure already computed: a near-tie between, say, `HYBRID` and `FULL_PIPELINE` becomes an apparently confident single label indistinguishable, to a classifier, from a query where one strategy clearly dominates. A ranking loss computed over the full utility vector does not require this collapse — a near-tie in the training data remains a near-tie in the training signal, and a well-formed ranking loss (§2, §5) is expected to reflect that as low-margin uncertainty in the model's output, rather than manufacturing false confidence where the oracle itself was ambivalent.

None of these arguments are novel to this project. Learning-to-Rank as a paradigm, and the pairwise/listwise loss formulations discussed in §5, are established results in the information retrieval literature predating this project by two decades. What is specific to TARA is the observation, made above, that this project's *own* dataset-construction procedure and *own* strategy taxonomy already exhibit the structural properties — graded utility, compositional candidates, tie-breaking-induced information loss — that motivate choosing a ranking formulation over a classification one for this particular problem.

## 2 Problem Formulation

Let $Q$ denote a developer query and $R$ denote the target repository, represented through its extracted context (`RepositoryContext`). Let $S = \{s_1, \ldots, s_7\}$ denote the fixed candidate set of retrieval strategies, corresponding to the seven members of `RoutingStrategy`.

For a given $(Q, R)$ pair and a candidate strategy $s \in S$, let

$$F(Q, R, s) \in \mathbb{R}^d$$

denote a $d$-dimensional feature vector describing the pair $(Q, R)$ *together with* candidate $s$. This is the standard query–document feature construction from the Learning-to-Rank literature, adapted here with $s$ playing the role a candidate document would play in search ranking: some feature groups (§3, Query/Task/Repository/Structural Features) are constant across all seven candidates for a fixed $(Q, R)$, while one group (§3, Resource Features) varies by candidate, since it describes each strategy's cost and feasibility with respect to the specific repository state. Without this candidate-varying feature group, $F(Q, R, s)$ would be identical across all $s \in S$ and no ranking would be learnable at all — this is not an implementation detail but a structural requirement of the formulation, discussed further in §3.

Let $U(Q, R, s) \in \mathbb{R}$ denote the **true utility** of strategy $s$ for $(Q, R)$: the oracle-computed retrieval- or generation-quality metric produced by RTS's labeling procedure (`docs/DATASET_DESIGN.md` §4). $U$ is observed, for training purposes, only on the finite set of labeled examples in RTS; it is the target the learned ranking policy is trained to approximate the *ordering* (and, where feasible, the *relative magnitude*) of.

A **ranking policy** $\pi: \mathbb{R}^d \to \mathbb{R}$ is a learned scoring function. Applied to every candidate for a fixed $(Q, R)$, it induces a predicted ranking

$$\sigma(Q, R) = \operatorname*{argsort}_{s \in S} \; \pi(F(Q, R, s)) \quad \text{(descending)}.$$

The **optimization objective** is to select $\pi$ minimizing expected ranking loss over the distribution $\mathcal{D}$ RTS's training split is drawn from:

$$\pi^{*} = \operatorname*{argmin}_{\pi} \; \mathbb{E}_{(Q,R) \sim \mathcal{D}} \Big[ \, \mathcal{L}\big( \{\pi(F(Q,R,s))\}_{s \in S}, \; \{U(Q,R,s)\}_{s \in S} \big) \Big],$$

where $\mathcal{L}$ is a ranking loss — a pairwise or listwise objective, as discussed in §5, in preference to a pointwise regression or classification loss, for the reasons given in §1.

The system's final output, the **ranked retrieval plan** $P$, is the ordered sequence of (strategy, predicted-score) pairs

$$P = \big[(s_{(1)}, u_{(1)}), (s_{(2)}, u_{(2)}), \ldots, (s_{(7)}, u_{(7)})\big], \quad u_{(1)} \geq u_{(2)} \geq \cdots \geq u_{(7)},$$

which is handed to the (unmodified) `RetrievalPlanner` for execution-parameter assignment, exactly as `ROUTER_DESIGN.md` §8 specified for the classification-based router — this architectural boundary is preserved unchanged by the reformulation, since it was already established to be orthogonal to *how* a strategy ranking or label is produced (`DESIGN_DECISIONS.md` §2).

## 3 Input Representation

Each feature group below is either constant across all seven candidates for a fixed $(Q,R)$ (a "shared" group, broadcast identically into $F(Q,R,s)$ for every $s$) or varies by candidate (the one "candidate-conditioned" group). This distinction, made explicit here because it is easy to elide, is what separates a genuine ranking formulation over $(Q,R,s)$ triples from a classification formulation over $(Q,R)$ pairs relabeled as a ranking after the fact.

**Query Features** *(shared)*. Surface properties of the query text itself, independent of the existing classifier's judgment: token count, quoted-identifier count, a coordinating-conjunction/multi-clause indicator, and, optionally, a dense query embedding (§7 of `ROUTER_DESIGN.md`'s equivalent discussion applies unchanged: this is an optional, separately ablated feature, not a default, since it couples the model to embedding-model availability and adds a per-query computation cost). This group exists to give the model access to query complexity signals independent of, and complementary to, the categorical judgment the next group provides.

**Task Features** *(shared)*. The complete `TaskClassification` object: `task_type` (13-way), `confidence`, the four boolean requirement flags, `extracted_keywords`, `detected_symbols`, `detected_file_paths`, `language_hint`. Included in full, not only `task_type`, for the same reason `ROUTER_DESIGN.md` §2 gave: the ranker must have access to at least as much information as the deterministic router it is compared against.

**Repository Features** *(shared)*. Coarse, relatively static descriptive properties of the target repository: language, domain category, size bucket, `file_count`, `symbol_count`.

**Structural Features** *(shared)*. The current, dynamic *state* of the repository's extracted context, distinct from the static descriptive properties above: graph node/edge counts, graph density, and embedding presence/dimensionality. This group is separated from Repository Features because these values can change independent of the repository's descriptive identity — a repository's size bucket does not change between one context-extraction run and the next, but whether its embeddings have been computed yet can.

**Resource Features** *(candidate-conditioned — the group that makes this a ranking problem)*. For each candidate strategy $s$: whether $s$ requires graph traversal and whether the repository's graph is populated (a compatibility indicator, softening rather than replacing the deterministic capability gate already implemented in `RetrievalPlanner`, `DESIGN_DECISIONS.md` §2); whether $s$ requires dense retrieval and whether embeddings exist; the number of retrievers $s$ invokes (a cost proxy); and $s$'s position in `RETRIEVER_EXECUTION_PRIORITY` (`tara.routing.strategy`), an existing cheap-to-expensive ordering reused here as a numeric cost feature rather than redefined. This is the only feature group that differs across the seven rows constructed for a single $(Q,R)$ training or inference instance.

## 4 Output Representation

**Ranked retrieval strategies.** The primary output is the ordered sequence $P$ defined in §2 — all seven strategies, ordered by descending predicted utility, not only the top choice.

**Utility scores.** The raw values $\pi(F(Q,R,s))$ accompanying each ranked strategy. These are **not** assumed to be on an interpretable absolute scale (e.g., directly readable as an expected Recall@k) unless separately validated: most pairwise and listwise ranking losses (§5) optimize *relative* order correctness, not *absolute* score calibration, and treating raw ranking scores as if they were calibrated utility estimates without validation would be an unsupported claim.

**Confidence.** Derived from the margin between the top two predicted scores, $u_{(1)} - u_{(2)}$, rather than borrowed from a classifier's softmax margin (which does not exist in this formulation) — a large gap indicates the model found a clearly preferable candidate; a small gap indicates a near-tie, directly operationalizing the uncertainty-preservation property argued for in §1.

**Probability distribution.** Not a native byproduct of most ranking objectives (unlike a softmax classifier's output). Where a probability-like object is needed — e.g., for compatibility with the calibration evaluation in §7 — one is constructed post hoc, either by a softmax over the raw scores or, for a listwise method built on a Plackett–Luce permutation model (ListNet, §5), by the model's own native permutation-probability formulation. Whichever construction is used, whether the resulting distribution is *calibrated* (in the sense of matching empirical outcome frequencies) is an open empirical question, not a property guaranteed by either construction, and must be validated exactly as the classification-based router's confidence was (`ROUTER_DESIGN.md` §6).

**Top-k execution.** The default consumption mode, preserving exact compatibility with the current `RetrievalPlan`/`RetrievalPlanner` contract, is top-1: the highest-ranked strategy is executed, identically to how the deterministic and classification-based routers' single predictions are consumed today. A top-k consumption mode — executing or falling back through the top two or three ranked strategies — is a natural extension this formulation makes available essentially for free (the full ranking already exists as a byproduct), directly realizing the fallback/contingency output that `docs/methodology/Adaptive_Retrieval_Definition.md` §5 named as a proposed, unimplemented candidate router output for the deterministic router. Adopting it would require changes to `RetrievalPlanner` not scoped by this document, and is treated here as a documented future option (§11), not a current design commitment.

## 5 Candidate Learning-to-Rank Algorithms

| Method | Family | Advantages | Disadvantages | Data requirements | Interpretability | Inference cost |
|---|---|---|---|---|---|---|
| LightGBM LambdaRank | Gradient-boosted trees, pairwise, metric-aware | Directly optimizes NDCG-like objectives via metric-weighted pairwise gradients; native handling of mixed tabular features; mature, widely used tooling | Requires grouped training data (query groups with per-candidate labels) — satisfied by RTS's oracle labeling by construction, given the schema extension noted at the top of this document | Moderate — tree ensembles are comparatively data-efficient at RTS's scale | High — per-instance feature attribution via standard tree-based methods | Low (tree traversal; sub-millisecond to low-single-digit ms) |
| XGBoost Ranker | Gradient-boosted trees, pairwise/listwise objectives | Same family and profile as LambdaRank; comparable accuracy, sometimes preferable regularization control | Largely interchangeable with LambdaRank; the choice between the two is closer to an engineering preference than a different modeling approach | Same as LambdaRank | High, same mechanism as LambdaRank | Low, same profile |
| RankNet | Neural, pairwise | Historically foundational; established basis LambdaRank itself was built to improve upon | Optimizes pairwise classification accuracy, not a ranking metric directly — precisely the gap LambdaRank was later designed to close; higher data requirement than tree-based methods | Higher than tree-based methods | Low — requires post-hoc explanation methods | Moderate, depends on network size |
| ListNet | Neural, listwise (Plackett–Luce) | Listwise objective more directly aligned with whole-ranking quality than pairwise objectives; native permutation-probability output is directly useful for §4's probability-distribution discussion | Listwise loss computation is more involved; less mainstream tooling support than gradient-boosted rankers; same neural data/interpretability concerns as RankNet | Higher than tree-based methods | Low | Moderate |
| Neural Learning-to-Rank (general) | Neural, various | Highest representational capacity; could jointly learn representations from raw query text rather than relying solely on engineered features; most extensible toward future end-to-end designs | Highest overfitting risk at RTS's scale (the same concern already raised for the analogous neural candidate in `ROUTER_DESIGN.md` §5/§11); least interpretable; latency depends on architecture | Highest | Low | Variable, potentially highest |

**Recommendation.** A gradient-boosted-tree pairwise ranker — LightGBM LambdaRank, or, largely interchangeably, XGBoost's ranking objective — is recommended as the primary candidate, for reasoning directly parallel to `ROUTER_DESIGN.md` §5's recommendation of gradient-boosted trees for the classification formulation: appropriate data efficiency at RTS's projected scale, low inference cost compatible with this project's latency-consciousness, and native per-instance interpretability preserving the explanation-generation requirement — now additionally justified by directly optimizing a ranking-quality objective (NDCG) rather than a proxy loss, which the classification formulation could not do at all. RankNet, ListNet, and general neural Learning-to-Rank are retained as documented, lower-priority alternatives, to be revisited if RTS's realized scale substantially exceeds current projections (§10).

## 6 Training Pipeline

**Dataset.** RTS (`docs/DATASET_DESIGN.md`), train split only for model fitting, validation split for model/hyperparameter selection, test split touched once for final evaluation — the identical sealing discipline used throughout this project (`DATASET_PLAN.md` §8, `EVALUATION_PROTOCOL.md` §14). Each training instance is a **query group**: the seven $(Q,R,s)$ rows sharing a fixed $(Q,R)$, each carrying its own $U(Q,R,s)$ label. As stated at the top of this document, this requires RTS to retain the full per-strategy utility vector, not only the arg-max `best_strategy` label currently specified as the primary output field in `docs/DATASET_DESIGN.md` §3.

**Feature extraction.** §3's five feature groups, computed per row, with four groups broadcast identically across a group's seven rows and Resource Features varying per row.

**Missing/infeasible candidates.** Where a strategy's oracle utility could not be computed for a given $(Q,R)$ (e.g., an execution failure during oracle labeling), the row is retained with an explicit sentinel low-utility value rather than dropped, preserving the fixed seven-candidate group size most gradient-boosted ranking implementations expect.

**Training.** The recommended method (§5) is trained on the full set of query groups from the train split, with the ranking loss operating within each group (pairwise or listwise comparisons are only ever made between candidates sharing the same $(Q,R)$, never across groups).

**Validation.** Model and hyperparameter selection is driven by ranking-appropriate metrics (§7 — principally NDCG@k) computed on validation-split query groups, not by classification metrics such as accuracy or F1, which are inappropriate model-selection criteria for a ranking objective.

**Inference.** At inference time no query group with known utilities exists — that is what is being predicted. The model scores all seven candidates for the query at hand, producing the output representation of §4.

**Evaluation.** §7's metrics, computed on the sealed test split, feeding into the identical downstream comparison methodology used throughout this project (paired Wilcoxon signed-rank, Holm–Bonferroni correction, BCa bootstrap confidence intervals — `EXPERIMENT_PLAN.md` §6, `EVALUATION_PROTOCOL.md` §6). This reformulation makes a three-way system-variant comparison available for the first time — the deterministic `AdaptiveRouter`, the classification-based learned router (`ROUTER_DESIGN.md`), and the ranking-based learned router specified here — evaluated on the identical TIQS test split under the identical statistical procedure, rather than the ranking-based router being assessed in isolation.

## 7 Evaluation Metrics

**NDCG (Normalized Discounted Cumulative Gain).** The primary router-internal metric, replacing macro-F1's role in the classification formulation. NDCG directly measures agreement between the predicted ranking and the utility-ordered true ranking, discounting lower positions and using actual utility magnitudes rather than only rank agreement — the one metric among those considered here that can reward a model for correctly representing a near-tie as a near-tie, operationalizing §1's central argument rather than merely asserting it.

**MRR (Mean Reciprocal Rank).** The reciprocal rank of the oracle-optimal strategy in the predicted ordering, averaged over queries. A coarser, more directly interpretable complement to NDCG, focused specifically on how highly the single best choice is ranked rather than the fidelity of the full ordering.

**Top-1 Accuracy.** Whether the top-ranked strategy matches the oracle `best_strategy` label. Retained specifically to keep this router directly comparable to the classification-based router (`ROUTER_DESIGN.md`) on a shared metric, despite being a lossier evaluation of the ranking model than NDCG.

**Top-3 Accuracy.** Whether the oracle-optimal strategy appears anywhere in the top three ranked candidates. A more forgiving diagnostic that distinguishes "wrong but close" from "wrong," and the direct evaluation instrument for whether a future top-k execution mode (§4) would plausibly help.

**Latency.** Inference-time cost, measured and disclosed under the same hardware-reporting discipline as every other timed result in this project (`EVALUATION_PROTOCOL.md` §8), compared explicitly against the deterministic router's existing sub-2ms measured budget — a design goal for the recommended candidate (§5), not an assumed property.

**Calibration Error.** Expected Calibration Error over the probability distribution constructed per §4. Included with an explicit caveat, restated from §4: calibrating a ranking model's scores is less theoretically standard than calibrating a classifier's native probabilistic output, since most ranking losses optimize relative order, not absolute probability mass. This metric tests a property the training objective does not directly target, and a favorable or unfavorable result should be interpreted accordingly, not treated as a foregone conclusion either way.

**Cross-repository generalization.** Ranking-quality metrics (NDCG, MRR, Top-k accuracy) computed separately per test-split repository, not only in aggregate, reusing the repository-level train/validation/test split already established in `DATASET_PLAN.md` §6–§8. Included specifically because a model that performs well only by exploiting idiosyncrasies of a small number of training repositories would be a materially different, and less useful, result than one that generalizes evenly across the held-out set — the direct measurement instrument for the distribution-mismatch and cold-start risks named in §9.

## 8 Expected Advantages

The following are **hypotheses requiring empirical validation**, not established results. Each is phrased to be directly testable against the classification-based router (`ROUTER_DESIGN.md`) as a comparison point, per §6's three-way evaluation design.

- **H-R1 (sample efficiency).** Because each training example supplies a full utility ordering rather than a single label, the ranking formulation is hypothesized to make more efficient use of RTS's limited label volume than the classification formulation, manifesting as a smaller performance gap between models trained on partial versus full training-set size — directly testable via the training-set-size ablation already reusable from `ROUTER_DESIGN.md` §10.
- **H-R2 (near-tie robustness).** The ranker is hypothesized to exhibit lower error concentrated specifically on queries where multiple strategies have similar true utility (near-ties, per §1), relative to the classifier, which is forced to commit to a single tie-broken label at training time — testable via a stratified error analysis comparing near-tie and clear-margin query subsets.
- **H-R3 (fallback robustness, contingent).** *If* a top-k execution mode (§4) is implemented in `RetrievalPlanner`, the availability of a full ranking rather than a single prediction is hypothesized to improve robustness when the top-ranked strategy's execution yields insufficient results. This hypothesis cannot be tested until that planner extension exists, and is explicitly conditional, not a claim about the current system.
- **H-R4 (calibration quality).** The margin-based confidence signal (§4) is hypothesized to be better calibrated than the classification-based router's softmax margin, since NDCG-style training directly rewards correctly spacing candidates by their true utility difference rather than only separating a single correct class from the rest — testable via a direct ECE comparison between the two routers under §7's calibration protocol.

## 9 Risks

- **Data bias.** RTS's stratified, non-natural query distribution (`docs/DATASET_DESIGN.md` §7) risks biasing the *learned ordering itself*, not only a classification prior: if certain task types are over-represented, utility patterns typical of those task types could dominate the learned ranking function's behavior even for underrepresented ones.
- **Oracle bias.** The oracle utility labels are only as trustworthy as the ground-truth relevant-context set and retrieval-quality metric used to compute them (`docs/DATASET_DESIGN.md` §7). If, for instance, ground-truth relevant-context annotation systematically under-captures structural relationships relative to file/symbol-level relevance, oracle utility for graph-involving strategies could be systematically underestimated, and the ranker would learn to underrank them for reasons unrelated to their genuine usefulness — a sharper, ranking-specific articulation of the construct-validity concern raised more generally in `EXPERIMENT_PLAN.md` §14.
- **Repository drift.** A model trained on utility patterns observed at a repository's pinned commit (`DATASET_PLAN.md`'s freezing protocol) may not reflect that same repository's later state, particularly as structural features it relies on (e.g., graph population, per `ROADMAP.md` M7) change over time.
- **Cold start.** For a genuinely novel repository outside RTS's training distribution — not merely a held-out test-split repository, which still shares RTS's overall characteristics — the ranker has no repository-specific learned prior and must generalize entirely from other training repositories. This is an asymmetry worth stating plainly: the deterministic router's rules were never fit to any specific repository and are cold-start-safe by construction; the learned ranker's cold-start behavior is an open empirical question, not a guaranteed property.
- **Generalization.** The broader version of the above two risks, directly measured by the cross-repository generalization metric (§7) rather than left as an unmeasured concern.
- **Label noise.** Beyond the general noise sources already named for RTS (`docs/DATASET_DESIGN.md` §7), pairwise ranking losses are specifically sensitive to systematically mis-ordered pairs: if the tie-breaking convention (preferring cheaper strategies within a margin) does not reflect genuine relative utility in some subset of cases, the learned ranking function could acquire a directionally consistent bias toward cheaper strategies that compounds across the whole strategy space — a qualitatively different failure mode than a classifier's independent per-example label errors.

## 10 Limitations

- This document's core dependency — retaining the full per-strategy utility vector in RTS — is a recommended, not yet executed, revision to `docs/DATASET_DESIGN.md`. Every section above assumes that revision is made; none of it is executable against the currently-specified schema alone.
- RTS's projected scale (2,000–5,000 examples) is small relative to typical Learning-to-Rank literature benchmarks, which commonly involve tens of thousands to millions of labeled query–document pairs. Results obtained at this project's scale should be interpreted with that difference in mind, not assumed comparable to published Learning-to-Rank results obtained under substantially different data regimes.
- The candidate set size (seven strategies, fixed) is considerably smaller and more constrained than typical Learning-to-Rank applications (web search ranking over potentially thousands of candidate documents). Intuitions and method rankings from that literature may not transfer cleanly to a seven-candidate setting, and this difference should temper expectations about which method "wins" here relative to general Learning-to-Rank benchmarks.
- The probability-distribution and calibration story (§4, §7) is less theoretically settled for ranking models than for classifiers; any calibration claim requires dedicated validation and should not be assumed by analogy to the classification-based router's more standard calibration story.
- This document does not resolve how `RetrievalPlanner` should consume a ranking rather than a single strategy, should top-k execution (§4) ever be adopted — that is separate, unscoped future design work.
- As with the classification-based router before it (`ROUTER_DESIGN.md` §11), any observed advantage over the deterministic router remains bounded by the same evaluation-instrument circularity: the oracle utilities this ranker is trained and evaluated against are defined using this project's own retrieval metrics, so superiority on this benchmark is necessary but not sufficient evidence of genuinely better routing.

## 11 Future Work

- **Online learning.** Incrementally updating the ranking function from live usage feedback rather than only from periodically retrained static batches, once a feedback loop exists — extending, for the ranking formulation specifically, the online/continual-learning future work already named for the classification-based router (`ROUTER_DESIGN.md` §12).
- **Bandit routing.** Treating strategy selection as a contextual bandit problem in which the ranker's predicted scores serve as an initial policy, refined by observed downstream reward over time. This specializes, rather than replaces, the contextual-bandit alternative already considered and deliberately deferred in `docs/methodology/Adaptive_Retrieval_Definition.md` §9 (deferred there for lack of an online feedback loop): a ranking function's per-candidate scores are conceptually the same kind of object as a bandit's action-value estimates, making the ranking formulation a more natural bridge to this future direction than the classification formulation was.
- **Feedback-driven adaptation.** Supplementing, or eventually replacing, oracle-metric-derived utility labels with real usage signals (e.g., whether generated code was accepted) — directly addressing the oracle-bias risk (§9), while acknowledging that usage-derived signals introduce their own distinct biases (e.g., survivorship bias toward whatever is used most) rather than being an unqualified improvement.
- **Continual learning.** Periodic retraining or incremental model updates as RTS grows and as repositories drift (§9), with explicit versioning and monitoring to detect when retraining is warranted — extending the model-freezing and versioning discipline already established for the classification-based router (`ROUTER_DESIGN.md` §6) from a one-time frozen artifact into an ongoing lifecycle.
