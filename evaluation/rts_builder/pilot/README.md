# RTS Builder — Pilot (scientific validation phase)

Produces the **first pilot Retrieval Training Set**: runs the frozen,
accepted Dataset Builder subsystem end-to-end, then adds exactly what
turns its output into an *immediately LTR-usable* dataset — a
deterministic train/validation/test split, automated validation against
the pilot's Success Criteria, quality-report figures, and dataset
documentation.

> See [`Architecture.md`](Architecture.md) for the full stage-by-stage
> diagram and [`VALIDATION_GUIDE.md`](VALIDATION_GUIDE.md) for exactly
> what is checked and how to read `validation_report.md`.

## Scope

```
manifest.json + queries.jsonl → DatasetGenerator (frozen) → grouped rows
    → split (train/val/test) → validate → export (parquet/jsonl) → figures → docs
```

1. **PilotRunner** (`runner.py`) — the outer loop: runs `DatasetGenerator`, then assembles/splits/validates/exports/documents its output.
2. **Assembler** (`assembler.py`) — reads Dataset Builder's grouped-format output, filters to the current run's `pipeline_digest`/`input_digest`, flattens to per-strategy rows, enriches with `query_id`/`metadata`.
3. **QuerySplitter** (`splitter.py`) — deterministic, hash-based train/validation/test assignment, one decision per query.
4. **PilotValidator** (`validator.py`) — the Success Criteria (missing values, duplicates, exactly-four-rows-per-query) plus descriptive statistics.
5. **exporter.py** — writes `train`/`validation`/`test` as Parquet and JSONL, and `feature_statistics.csv`.
6. **figures.py** — the six required quality-report PNGs.
7. **reporting.py** — renders `validation_report.md`, `data/README.md`, `DATASET_CARD.md`.

Repository Loader, Parser, Feature Extraction, Retrieval Executor,
Oracle Utility, and Dataset Builder are frozen and **not modified** by
this subsystem — every one of their models, settings classes, and
digest/checkpoint semantics is reused exactly as accepted. Learning-to
-Rank model training, the planner, task classification, LLM inference,
and paper writing are not present here.

## Usage

```python
from pathlib import Path

from evaluation.rts_builder.dataset_builder.query_iterator import QueryIterator
from evaluation.rts_builder.dataset_builder.repository_iterator import RepositoryIterator
from evaluation.rts_builder.pilot.config import PilotSettings
from evaluation.rts_builder.pilot.runner import PilotRunner

repositories = RepositoryIterator(Path("manifest.json"))   # 8 repositories, see DatasetSchema.md
queries = QueryIterator(Path("queries.jsonl"))              # 150-200 queries, see DatasetSchema.md

runner = PilotRunner(settings=PilotSettings(data_dir="data"))
summary = runner.run(repositories, queries)

print(summary.validation_report.passed, summary.validation_report.row_count)
```

This is a two-stage run every time: Dataset Builder's own checkpoint
/resume semantics apply unchanged to the first stage (re-running the
identical command resumes an interrupted `DatasetGenerator` run exactly
as documented in its own `README.md`), and the pilot's split assignment
is deterministic (same `split_seed` + same query → same split, every
time — see `Architecture.md`).

### Producing the actual pilot-scale dataset

`PilotRunner` is input-data-agnostic: it runs against whatever
`manifest.json`/`queries.jsonl` it's given, at any scale. Reaching the
pilot's target scale (8 repositories, 150-200 queries with real,
curated ground-truth relevance judgments) requires supplying those two
files — this subsystem deliberately does not author queries or
relevance judgments itself (see "Inputs" below), consistent with every
prior RTS Builder milestone's own established scope boundary.

## Inputs (externally authored, not generated by this subsystem)

Identical to Dataset Builder's own inputs — see its `DatasetSchema.md`
§1: `manifest.json` (repository manifest) and `queries.jsonl` (queries
+ ground-truth relevance grades). This subsystem does not add, remove,
or reinterpret any input field; it consumes `RepositoryIterator`/
`QueryIterator` exactly as Dataset Builder already validates them.

## Configuration

All settings are optional and environment-driven via `PilotSettings`
(prefix `RTS_PILOT_`). See [`.env.example`](.env.example).
`PilotRunner` additionally accepts a `dataset_generator`/
`dataset_settings` pair for full control over the underlying Dataset
Builder run (e.g. non-default `PipelineOrchestrator` collaborators);
`enable_grouped_export` is forced to `True` on whatever
`DatasetBuilderSettings` is used, since the assembler requires Dataset
Builder's grouped-format output.

Key options:

| Setting | Default | Purpose |
|---|---|---|
| `train_ratio` / `validation_ratio` / `test_ratio` | `0.70` / `0.15` / `0.15` | Must sum to `1.0` (validated at construction). |
| `split_seed` | `"tara-rts-pilot-v1"` | Salt for the deterministic per-query split hash — keep fixed for a stable split across pilot runs. |
| `expected_strategy_count` | `4` | How many strategy rows a query must have to pass the "every query has exactly four strategy rows" check. |
| `fail_on_validation_error` | `True` | If `True`, a failed blocking check raises `PilotValidationError` and no split/figure/doc files are written. If `False`, the run proceeds and the failure is only visible in `validation_report.md`. |

## Design Decisions

- **The pilot layer never modifies a frozen model.** `query_id`,
  `metadata`, and `split` — the three columns this subsystem adds to
  the Output Schema beyond Dataset Builder's own — are stamped onto
  plain flat `dict` rows in `assembler.py`/`runner.py`, never added as
  fields on `DatasetRow`/`GroupedDatasetRecord`/`StrategyOracleRow`/
  `FeatureVector`. Composing at the dict layer, not the frozen-model
  layer, is what keeps this a genuinely new subsystem rather than a
  redesign of an accepted one.
- **Splitting is a pure hash function of `(split_seed, repository_id,
  commit_sha, query_text)`, not a seeded shuffle.** A shuffle-based
  split would need the *entire* query population in memory at once and
  would silently reassign every query's split if the population's size
  or order ever changed between runs. The hash-based approach assigns
  each query independently: a query's split never depends on any other
  query's presence, so growing the query population later does not
  reshuffle previously-assigned queries — deterministic and stable by
  construction, not by discipline.
- **The pilot reads Dataset Builder's *grouped* output, not its
  long-format output.** The grouped format's one-record-per-query shape
  is exactly the unit both split assignment and `query_id` computation
  need; reading the long-format file would require re-grouping by
  `(repository_id, commit_sha, query_text)` first, which the grouped
  file already provides.
- **Rows are filtered to the current `pipeline_digest`/`input_digest`
  before anything else happens** (validation, splitting, export).
  Dataset Builder's checkpoint invalidation is whole-file but
  non-destructive — a digest change causes recomputed rows to be
  *appended*, not replace, a prior run's now-superseded ones (see its
  `README.md`'s Reproducibility Guarantees). Skipping this filter would
  let stale, superseded rows leak into the pilot dataset and inflate
  every count.
- **Validation is computed independently of `DatasetStatistics`,
  not by reusing `StatisticsAccumulator`.** Both read the same
  underlying rows, but recomputing from scratch here means a bug in one
  is unlikely to be silently masked by the other, and lets
  `PilotValidator` check things Dataset Builder was never asked to
  check (missing values, duplicate rows, exactly-four-rows-per-query).
- **`fail_on_validation_error` defaults to `True`.** Writing
  `train.parquet`/`DATASET_CARD.md`/figures over a dataset already
  known to have failed a blocking Success Criterion would let a broken
  pilot look shippable at a glance. The default fails loudly instead;
  setting it `False` is an explicit, opt-in choice for inspecting a
  failing run's data during debugging.
- **Figures are static PNGs, not an interactive artifact.** This is a
  written quality report for a dataset build, not a dashboard — no
  hover/tooltip/theme-toggle layer is needed or built. Color choices
  still follow the project's data-visualization method (fixed
  categorical order for the four strategies, single-hue sequential
  ramps for magnitude, a diverging ramp for the correlation matrix,
  hue+marker-shape composite encoding for the one all-pairs scatter) —
  see `figures.py`'s module docstring.

## Failure Modes

| Failure | Behavior | Notes |
|---|---|---|
| Dataset Builder's grouped export is disabled | `PilotAssemblyError`, raised before any validation/export | `PilotRunner` forces `enable_grouped_export=True` when it builds its own default `DatasetGenerator`; only reachable if a caller passes a pre-built `dataset_generator` with grouped export off. |
| A blocking Success Criterion fails and `fail_on_validation_error=True` (default) | `PilotValidationError`, carrying the full `ValidationReport`; no split/statistics/figure/doc files written | See "Design Decisions". The underlying Dataset Builder output (long-format/grouped files, checkpoint, `digest.json`) is still written — only the pilot's own downstream artifacts are withheld. |
| A blocking Success Criterion fails and `fail_on_validation_error=False` | Run completes normally; `validation_report.md`'s `passed: false` and the failing check(s) are the only signal | Opt-in, for debugging a failing pilot's actual data. |
| Every input error Dataset Builder itself can raise (`ManifestError`, repository/query failures, etc.) | Unchanged — propagates or is logged/skipped exactly as documented in Dataset Builder's own `README.md` | This subsystem adds no new handling around Dataset Builder's own generation stage. |
| A split ends up empty (e.g. a tiny/unbalanced input population) | Not an error; that split's Parquet/JSONL files are written with zero rows (Parquet still gets the full, correctly-typed schema) | Expected at very small scale; at the pilot's target scale (150-200 queries) this is not a realistic outcome for the default 70/15/15 ratios. |
| A figure fails to render (e.g. disk full) | `PilotError`, propagates, aborts the run | Figures are written after validation has already passed — a figure-write failure is treated as an infrastructure problem, not a data-quality one. |
