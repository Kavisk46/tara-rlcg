# Research Notes — FastAPI Pilot Annotation Run

Reflective notes from constructing this pilot run against FastAPI at
commit `a375f6b948b99fa4260129856bbf11d037f363ef`. These are
observations and judgments, not additional data -- everything factual
referenced here was already established in `repository_summary.md`,
`annotation_drafts.jsonl`, or `validation_report.md`.

## 1. Interesting observations

- **FastAPI's own package is thinner than its reputation suggests.**
  Of `fastapi/`'s 48 files, several of the most "important"-sounding
  modules by name (`websockets.py`, `staticfiles.py`, `templating.py`,
  `testclient.py`, `requests.py`, most of `middleware/`) are 1-3 line
  re-exports of Starlette. The actual FastAPI-specific logic is heavily
  concentrated in a small number of large files: `routing.py` (6,447
  lines), `applications.py` (4,774 lines), `param_functions.py` (2,460
  lines), and `dependencies/utils.py` (1,053 lines) together account for
  a large majority of the package's ~14,900 inspected lines.
- **The test suite is disproportionately large relative to the
  package**: 593 test files against 48 package files (~12:1), and
  `tests/test_tutorial/` mechanically mirrors `docs_src/`'s directory
  structure -- documentation examples are first-class, tested code in
  this repository, not illustrative snippets that could silently rot.
- **The duplicated-`auto_error`-pattern finding (fastapi-009) was
  stronger evidence than expected** for a hand-picked refactor query --
  confirmed identically repeated across `HTTPBase`/`HTTPBasic`/
  `HTTPBearer`/`HTTPDigest` in one file and `OAuth2`/
  `OAuth2PasswordBearer`/`OAuth2AuthorizationCodeBearer` in another.
  This is the kind of concrete, verifiable duplication a refactor query
  benefits from having behind it.
- **Two "obvious" answers turned out to be subtly wrong on closer
  reading**: (1) `use_cache` (fastapi-017) looks like the answer to "a
  dependency that runs once" but is verified to be per-*request*
  -scoped, not per-*application*-scoped; (2) numeric path/query
  constraint error messages (fastapi-004) are NOT generated by any code
  in this repository -- they come from Pydantic's `TypeAdapter`
  directly. Both are documented in `annotation_drafts.jsonl` precisely
  because a shallower search would have missed them and produced a
  confidently wrong candidate.

## 2. Unexpected repository structure

- `docs/` (multi-language rendered site) and `docs_src/` (executable
  examples) are easy to conflate by name but serve entirely different
  roles -- only `docs_src/` is tested code; `docs/en/docs/` (prose
  Markdown) was not searched in this pass at all (an acknowledged gap,
  not a hidden one -- see `human_annotation_checklist.md` §4).
- The `_compat/` package only contains a `v2.py` (Pydantic v2 support)
  at this commit -- no `v1.py` was found despite the file being named
  generically (`_compat`, not `_compat_v2`). This is worth independent
  confirmation (see Threats to Validity) since it affects how
  confidently "the validation layer" can be pointed to as a single
  file for any given query.
- `fastapi/security/base.py` is only 6 lines -- a single class
  definition (`SecurityBase`) with two class-level type annotations
  and no methods. Its small size belies its structural importance
  (every security scheme subclasses it, directly or indirectly).

## 3. Potential annotation difficulties

- **fastapi-011 and fastapi-013 may not be annotatable as originally
  worded.** fastapi-011 (refactor middleware error handling) has no
  confirmed error-handling logic anywhere in `fastapi/middleware/` to
  refactor. fastapi-013 (intermittent concurrency test) has no
  confirmed existing flaky test. Forcing a human annotator to assign
  relevance grades to speculative candidates for either query risks
  producing ground truth that reflects "the closest thing I could
  find" rather than genuine relevance -- a subtle but real corruption
  risk for the training signal. **Recommendation: the human annotator
  or a query-review pass should explicitly decide to either replace
  these two queries or accept them as intentionally hard/near-empty
  relevance cases (which is itself a valid, if unusual, training
  signal for a retrieval system -- "sometimes nothing is relevant").**
- **Directory-level candidates (7 of them, see `validation_report.md`
  §4) require the annotator to do additional file-level enumeration
  work this run did not do**, specifically to avoid guessing a
  specific filename inside a directory whose contents were only
  confirmed to exist, not individually read.
- **fastapi-002's premise (CORS headers on exception responses)
  straddles a repository boundary** -- FastAPI's own code contributes
  at most half the picture; Starlette's `CORSMiddleware` (not present
  in this local checkout) is the other half. An annotator without
  access to Starlette's own source may not be able to fully resolve
  this query's relevance set from this repository alone.

## 4. Threats to validity

- **Single-annotator (AI) search, not yet cross-checked by a second
  independent pass.** Every candidate in this run came from one search
  process (this session). `RELEVANCE_ANNOTATION_HANDBOOK.md`'s
  double-annotation and inter-annotator-agreement machinery has not
  been applied to search-assistance itself, only to the eventual human
  grading step it feeds. A second, independent AI or human search pass
  over the same 20 queries would be a reasonable robustness check
  before treating this run's candidate lists as complete.
- **Search depth was uneven across queries.** Some queries (fastapi-001,
  fastapi-009) benefited from prior investigation in this same session
  and were read in unusual depth; others (fastapi-007, fastapi-018)
  relied more heavily on directory-listing-confirmed-but-content
  -unread candidates. This unevenness is disclosed per-candidate via
  the `uncertainty` field, but it does mean "confidence" is not
  perfectly comparable across queries.
- **No query was validated by actually reproducing its scenario.** No
  code was run, no test was executed, no bug was triggered. Every
  candidate reflects *structural* plausibility (the right function
  exists in the right place) rather than *behavioral* confirmation
  (the function actually misbehaves as the bug-fix queries describe).
  This is by design (`CRITICAL RULES`: never modify repository code),
  but it means this dataset's bug_fix queries in particular describe
  plausible-not-confirmed defects.
- **Pydantic v1-vs-v2 compatibility scope was not independently
  verified.** Only `_compat/v2.py` was found; whether this FastAPI
  version has fully dropped Pydantic v1 support, or whether v1 support
  exists elsewhere under a different name, was not checked against
  `pyproject.toml`'s full dependency constraints or changelog.
- **query_id/category/difficulty/notes fields are this run's own
  tracking metadata**, not part of the frozen `QuerySpec`/
  `RelevanceJudgment` pipeline schema (per `ANNOTATION_HANDBOOK.md` §5
  and `RELEVANCE_ANNOTATION_HANDBOOK.md` §10) -- a downstream merge
  step is still required before this data can feed `DatasetGenerator`,
  and that merge step has not been built or exercised in this run.

## 5. Future improvements

- Run a second, independent search pass (ideally by a different
  annotator or a fresh AI session with no memory of this one) over the
  same 20 queries and compute agreement on candidate sets, mirroring
  the inter-annotator-agreement discipline already defined for grading.
- Resolve the 7 directory-level candidates to specific files as a
  fast-follow before human review begins, reducing the checklist's
  workload.
- Decide the fate of fastapi-011 and fastapi-013 explicitly (replace
  vs. accept as near-empty-relevance cases) before this run is treated
  as ready for grading.
- Extend a future round's queries to cover the 23 currently-untouched
  `fastapi/` package files identified in `dataset_statistics.md` §7,
  particularly OpenID Connect security and CLI/docs-serving, which are
  entirely absent from this 20-query sample.
- Search `docs/en/docs/` directly for fastapi-015/fastapi-016 rather
  than relying on `docs_src/`'s executable-example proxy, once a
  documentation-page-aware search approach is available.
- Consider whether "no relevant file found" (fastapi-013's honest
  outcome) should be an explicitly supported, first-class query outcome
  in the pipeline's schema and statistics, rather than something that
  only shows up as an unusually short candidate list.
