# RTS Builder — Dataset Builder (Milestone 7, final assembly)

Composes all five prior, accepted-and-**frozen** RTS Builder milestones
(Repository Loader, Parser, Feature Extraction, Retrieval Executor,
Oracle Utility) into one end-to-end pipeline that produces the
Retrieval Training Set: the Learning-to-Rank training data.

> See [`Pipeline.md`](Pipeline.md) for the full stage-by-stage data
> -flow diagrams, [`DatasetSchema.md`](DatasetSchema.md) for the
> complete output schema, and [`REVIEW_RESPONSE.md`](REVIEW_RESPONSE.md)
> for an anticipated-reviewer self-assessment.

## Scope

```
Repository → Repository Loader → Parser → Feature Extraction → Retrieval Executor → Oracle Utility → RTS Dataset
```

1. **Pipeline Orchestrator** (`pipeline_orchestrator.py`) — runs the six frozen stages for one repository / one query.
2. **Query Iterator** (`query_iterator.py`) — reads an externally-authored queries file, keyed by `repository_id`.
3. **Repository Iterator** (`repository_iterator.py`) — reads an externally-authored repository manifest.
4. **Dataset Generator** (`dataset_generator.py`) — drives the orchestrator across every repository × query, with checkpointing and streaming export.
5. **Long-format dataset** — one row per `(query, strategy)`, JSONL/CSV/Parquet.
6. **Grouped dataset** — one record per query (four strategies nested), JSONL.
7. **Dataset statistics** — repository/query counts, strategy distribution, average utility/latency/quality (overall and per-strategy), feature statistics.
8. **Export** — JSONL, CSV, Parquet, all streaming and resume-safe.

Learning-to-Rank model training, the planner, task classification, and
the LLM interface are later RTS Builder milestones and are not present
here.

## Usage

```python
from evaluation.rts_builder.dataset_builder.config import DatasetBuilderSettings
from evaluation.rts_builder.dataset_builder.dataset_generator import DatasetGenerator
from evaluation.rts_builder.dataset_builder.query_iterator import QueryIterator
from evaluation.rts_builder.dataset_builder.repository_iterator import RepositoryIterator

repositories = RepositoryIterator(Path("manifest.json"))   # see DatasetSchema.md
queries = QueryIterator(Path("queries.jsonl"))              # see DatasetSchema.md

generator = DatasetGenerator(settings=DatasetBuilderSettings(output_dir=".rts_cache/dataset"))
summary = generator.generate(repositories, queries)

print(summary.statistics.query_count, summary.statistics.average_utility_overall)
```

Interrupting and re-running the identical command **resumes**: already
-checkpointed `(repository_id, commit_sha, query_text)` triples are
skipped, no rows are duplicated, and `summary.statistics` reflects the
*cumulative* dataset across every session, not just the newly
-processed queries -- **as long as the pipeline code/configuration and
input files are unchanged**. See "Reproducibility Guarantees" below for
what happens when they aren't (Reviewer Minor Revision).

## Inputs (externally authored, not generated by this subsystem)

- **Repository manifest** (`manifest.json`, a JSON array): `repository_id`, `source_url`, `commit_sha`, optional `metadata`. Mirrors `docs/DATASET_BUILDER_SPEC.md` §3's schema, narrowed to what `RepositoryLoader.load_repository` actually needs — see `DatasetSchema.md`.
- **Queries file** (`queries.jsonl`, one JSON object per line): `repository_id`, `query_text`, `relevance_grades` (ground-truth relevance, as `evaluation.rts_builder.oracle_utility.models.RelevanceJudgment` requires). Mirrors `docs/DATASET_BUILDER_SPEC.md` §4's "query text records, keyed by repository."

Neither query authoring nor relevance annotation is implemented here —
both are established, external, human/LLM-driven activities
(`docs/PILOT_EXECUTION_PLAN.md` §4), consistent with "Do NOT implement:
Task classifier" and this milestone's scope being orchestration, not
data authoring.

## Configuration

All settings are optional and environment-driven via
`DatasetBuilderSettings` (prefix `RTS_DATASET_`). See
[`.env.example`](.env.example). This milestone's own settings cover
only output locations/formats/batching; each of the five wrapped
stages keeps its own settings object, injected into
`PipelineOrchestrator` independently. `DatasetGenerator` additionally
accepts a `pipeline_settings: PipelineSettingsSnapshot`, used only to
compute `pipeline_digest`'s `configuration_hash` (see below) -- if you
construct `PipelineOrchestrator`'s five collaborators with non-default
settings, pass the identical settings objects here too, or the digest
will not accurately reflect what actually ran.

## Reproducibility Guarantees (Reviewer Minor Revision)

Resuming is only safe -- in the sense of "the resumed run's output is
indistinguishable from the original run having never stopped" -- when
nothing that could affect the computed values has changed. This
revision makes that condition explicit and machine-checked, rather than
an assumption resuming silently relied on before.

### `pipeline_digest`

A fingerprint of the **pipeline code and configuration**
(`digest.compute_pipeline_digest`), combining:

| Component | What it captures | How it's computed |
|---|---|---|
| `pipeline_version` | Dataset Builder's own orchestration-code version | A maintainer-bumped constant (`digest.PIPELINE_VERSION`) |
| `git_commit` | The TARA repository's own commit | `git rev-parse HEAD` (via GitPython), suffixed `-dirty` if the working tree has uncommitted changes; `"unknown"` outside a git checkout |
| `feature_schema_version` | `FeatureVector`'s current shape | A content hash of `FeatureVector.model_json_schema()` -- automatically changes if that frozen model's fields ever change, with no manual bump to forget |
| `oracle_schema_version` | `StrategyOracleRow`'s current shape | A content hash of `StrategyOracleRow.model_json_schema()`, same rationale |
| `configuration_hash` | Every wrapped stage's effective settings | A content hash of `PipelineSettingsSnapshot`'s six settings objects, JSON-canonicalized (`sort_keys=True`) |

All five combine (another content hash) into `digest_hash`, the value
actually used in the checkpoint key.

### `input_digest`

A fingerprint of the **externally-authored input files**
(`digest.compute_input_digest`): a SHA-256 of the repository manifest's
raw bytes, and a SHA-256 of the queries file's raw bytes, combined into
`digest_hash`. This pipeline's actual input schema (Milestone 7, not
redesigned by this revision) combines queries and their ground-truth
relevance grades into one file (`queries.jsonl`) rather than the
hypothetical separate `queries.json` / `relevance_judgments.json` files
a from-scratch design might use -- `queries_hash` alone already covers
100% of this pipeline's externally-supplied query/relevance data; no
third hash is needed or computed.

### Checkpoint invalidation is whole-file, not per-entry

If **any** loaded checkpoint entry was recorded under a different
`pipeline_digest` or `input_digest` than the current run's, the
**entire checkpoint** is treated as invalid for this run -- every query
is recomputed, not just the ones whose specific entry didn't match.
This was a deliberate design correction made while implementing this
revision (not the original plan): a per-entry invalidation policy
seemed more surgical at first, but interacts incorrectly with
cumulative statistics reseeding -- a recomputed query's contribution
would be double-counted (once from the stale seed in
`dataset_statistics.json`, once from its fresh recomputation), since
`pipeline_digest`/`input_digest` each describe the *whole run's*
configuration/inputs, not any one query's, so a change to either
logically means *every* query needs recomputing, not a mix of "trust
this one, recompute that one." See `REVIEW_RESPONSE.md` for the full
account of this correction.

**Consequence worth stating plainly**: appending even one new query to
`queries.jsonl` changes that file's hash, which invalidates the whole
checkpoint, which recomputes *every* query in it -- including ones
whose own text never changed. Growing a query population incrementally
across sessions without full recomputation is not supported by this
revision; it trades that ergonomic in favor of a stronger, simpler
-to-reason-about guarantee ("if the checkpoint says valid, the *entire*
recorded configuration and inputs are unchanged"). Nothing is
destructively deleted or rewritten when this happens: prior runs'
checkpoint entries and exported rows remain physically on disk,
harmless, and every exported row also carries the `pipeline_digest`
/`input_digest` of the run that produced it (see `DatasetSchema.md`),
so a consumer can always recover the current, de-duplicated view by
filtering to the values recorded in `digest.json`.

### `digest.json`

Every `generate()` call writes `<output_dir>/digest.json`: the full,
structured `pipeline_digest` and `input_digest` for that run, for
auditing "what exactly produced this dataset" without needing to
recompute anything. Overwritten each run with the latest digests;
historical digests for any specific row remain recoverable from that
row's own `pipeline_digest`/`input_digest` columns, or from
`checkpoint.jsonl`'s per-entry history.

## Design Decisions

- **Two-phase orchestration: per-repository stages run once, per-query
  stages run once per query.** Cloning and parsing a repository is
  expensive and query-independent; feature extraction, retrieval, and
  oracle computation are genuinely query-dependent. `PipelineOrchestrator`
  makes this split explicit (`run_repository_stages` /
  `run_query_stages`) rather than re-running the whole pipeline per
  query.
- **Checkpointing is per-`(repository_id, commit_sha, query_text)`, not
  per-repository.** A repository with 500 queries, interrupted after
  300, resumes at query 301 — it does not restart from query 1, and
  does not needlessly re-clone/re-parse (both of which have their own
  frozen caching anyway; skipped here purely to avoid wasted Retrieval
  Executor / Oracle Utility work when every one of a repository's
  queries is already done).
- **A checkpoint entry is written only after every enabled writer has
  durably succeeded**, never before or during. This is what makes
  "resume" and "retry a failed query" the same mechanism: a query whose
  computation raised, or whose write failed, is simply never
  checkpointed, and the next run picks it up automatically — no
  separate retry logic was needed.
- **Per-item failure isolation is split into two categories with two
  different failure policies.** Repository-load/parse failures and
  query-computation failures (Feature Extraction / Retrieval Executor /
  Oracle Utility) are caught, logged, and skipped — one bad repository
  or query must not abort a multi-hour run. Writer/checkpoint failures
  are **not** caught the same way: they propagate and abort the run,
  since they signal an infrastructure problem (disk full, permissions)
  that would otherwise silently masquerade as every subsequent query
  "failing" for an unrelated reason.
- **Dataset statistics are computed incrementally (`StatisticsAccumulator`),
  never by re-reading the exported files**, and can be *reseeded* from
  a previously-written `dataset_statistics.json`. This is what makes
  statistics correctly cumulative across a multi-session, resumed
  build, in O(1) memory relative to dataset size, without needing every
  export format to stay enabled or intact to recompute them. See
  `Pipeline.md`.
- **Long-format rows merge `FeatureVector` and `StrategyOracleRow`.**
  A Learning-to-Rank model trains on (features → label) pairs; a row
  containing only quality/utility/rank (the label) or only
  query/repository/graph/structural/resource features (the input)
  would not be directly usable on its own. `DatasetRow.to_flat_dict`
  merges both, verified disjoint by field-name prefix.
- **`PipelineSettingsSnapshot` cannot be auto-detected from an
  already-constructed `PipelineOrchestrator`.** Each of the five
  wrapped stages' settings classes is frozen, stores its settings in a
  private attribute, and exposes no public accessor -- so
  `configuration_hash` cannot introspect an orchestrator's actual
  collaborators without reaching into another milestone's private
  internals, which this subsystem does not do. The settings bundle is
  instead a second, explicit constructor argument a caller must keep in
  sync with whatever they passed to `PipelineOrchestrator` -- a
  caller-responsibility contract, not a magic one, and stated as such
  rather than silently assumed correct.
- **Schema versions are content hashes of the live Pydantic schema, not
  manually-bumped version strings.** A hand-maintained `"1.2.0"` can be
  forgotten when a field actually changes, silently defeating the
  entire point of `feature_schema_version`/`oracle_schema_version`
  (detecting that a change happened). `FeatureVector.model_json_schema()`
  /`StrategyOracleRow.model_json_schema()` cannot drift from the code,
  by construction.
- **Parquet cannot be safely appended to across separate process runs**
  (its footer/schema is finalized once, at `close()`); JSONL and CSV
  can. Long-format Parquet output is therefore a *directory* of
  uniquely-named part files, one per `DatasetGenerator` invocation — the
  same pattern Spark/Dask use for incrementally-built Parquet datasets
  — rather than a single file. A resumed run never touches a prior
  run's part file. Grouped output is JSONL-only: CSV/Parquet are
  fundamentally flat/tabular formats and do not naturally represent a
  nested per-query strategy array without either flattening it back
  into the long format or a lossy string-encoded workaround.

## Failure Modes

| Failure | Behavior | Notes |
|---|---|---|
| Repository manifest / queries file missing, malformed, or fails validation | `ManifestError`, raised at `RepositoryIterator`/`QueryIterator` construction | Fails fast, before any pipeline stage runs — curated input errors are not silently tolerated the way a crash-truncated checkpoint line is. |
| A specific repository fails to load or parse | Logged, `repositories_failed` incremented, that repository's queries are skipped this run | Not checkpointed — retried automatically on the next run. |
| A specific query fails during Feature Extraction / Retrieval Executor / Oracle Utility | Logged, `queries_failed` incremented, that query is skipped this run | Not checkpointed — retried automatically on the next run. |
| A writer or the checkpoint store fails to write (disk full, permissions) | `DatasetWriteError` / `CheckpointError`, propagates, aborts the run | Deliberately not caught per-query — see Design Decisions. Whatever was already durably written/checkpointed before the failure remains valid for the next resumed run. |
| Process crashes mid-write | The affected file may have one incomplete trailing line/row; the corresponding query was never checkpointed | Accepted, documented limitation (not solved via a write-ahead log): a resumed run reprocesses and re-appends that query, producing a duplicate-plus-truncated artifact a downstream loader should tolerate (e.g. `pandas.read_json(lines=True)` skips a malformed trailing line by default in permissive mode) or a consumer can de-duplicate on the row's `(repository_id, commit_sha, query_text, strategy_name)` key, or (more precisely, since Revision 3) filter to rows whose `pipeline_digest`/`input_digest` match the current `digest.json`. |
| `RelevanceJudgment` for a query has no relevant files at all | Not an error (Oracle Utility's own documented behavior); that query's rows all have `quality_score = 0.0` | Ranking falls back to latency alone for that query — a defensible, non-crashing degenerate case. |
| A checkpoint entry's `pipeline_digest`/`input_digest` don't match the current run's | Not an error; the *entire* checkpoint is treated as invalid, every query is recomputed | See "Reproducibility Guarantees". Logged at `WARNING` with the count of mismatched entries found. |
| `pipeline_settings` doesn't match what `PipelineOrchestrator`'s collaborators were actually constructed with | Not detectable; `configuration_hash` silently reflects the wrong configuration | A caller-responsibility contract, not automatically verified — see Design Decisions. |
| `digest.compute_input_digest`'s manifest or queries file vanishes between iterator construction and `generate()` | `DigestComputationError`, propagates, aborts the run | Narrow race; the files were already successfully read once (by `RepositoryIterator`/`QueryIterator`), so this indicates external deletion during the run, not a normal operating condition. |
